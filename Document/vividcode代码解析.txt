二、从整体看：两个程序，共用一套存储代码
============================================================

控制台程序：vividcode.exe
  入口：cli_main.cpp 中的 main()
  职责：接收命令，生成文件，清理记录，删除生成目录。

图形程序：vividcode-viewer.exe
  入口：main.cpp 中的 main()
  职责：显示文件列表、卡片和源码，打开或刷新项目。

共享部分：ProjectStore.cpp + ProjectScanner.h
  职责：保存记录和扫描文件，供两个程序重复使用。

可以把代码之间的关系读成下面这样：

  cli_main.cpp
      ├─ -g → VividCode::generate()
      ├─ -d → VividCode::removeGenerated()
      └─ -c → VividCode::cleanHistory()

  main.cpp
      └─ VividCodeWindow 窗口
          └─ openProject()
              ├─ scanProject()：找文件
              ├─ rebuildViews()：更新树和卡片
              ├─ showFile()：显示当前源码
              └─ recordIfInitialized()：需要时保存新记录

这些函数名对应真实代码，不表示每个函数都各自启动一个进程。
一次程序运行中，它们通常就是按调用顺序执行的普通 C++ 函数。

为什么有两个 main()，却不会报重复定义？
  因为 CMakeLists.txt 把它们分别编译进两个不同的 exe。
  不同程序可以各有一个 main()。
  ProjectLauncher.cpp 另有 WinMain 入口，单独编译为原生启动器；演示源码已删除。

共享静态库 vividcode_store 是什么？
  构建时先把 ProjectStore.cpp 编译成可复用代码，再链接进两个 exe。
  它不是要单独双击运行的程序，也不需要作为单独 DLL 随项目部署。

三、cli_main.cpp：控制台从哪里开始
============================================================

假设你在 E:\MyProject 中输入：
  vividcode -g

Windows 先通过 PATH 找到 vividcode.exe，然后执行 cli_main.cpp 的 main()。

主要步骤如下：
  1. 创建 QCoreApplication app(argc, argv)。
     它提供 Qt 非图形程序所需的基础环境，也方便取得命令行参数。
     当前 CLI 执行完任务就返回，不需要调用 app.exec() 等待窗口事件。

  2. 用 app.arguments() 获取参数列表。
     列表第 0 项是程序名，第 1 项才是 -g。
     所以“一条命令”对应 args.size() == 2。

  3. 检查参数。
     没参数或 -help：输出帮助。
     多个操作一起输入、未知参数：报参数错误，返回 2。

  4. 用 QDir::currentPath() 取得当前工作目录。
     这里得到的是 E:\MyProject，不是 exe 的安装目录。

  5. 根据参数调用 ProjectStore 中的函数。
     -g 还会传入 QCoreApplication::applicationDirPath()，
     告诉 generate() 从哪里复制已经编译好的查看器和 Qt DLL。

  6. 输出结果并退出。
     返回 0：操作成功；1：操作失败；2：命令参数错误。

一定要分清这两个路径：
  currentPath()        = 用户在哪个目录执行命令，决定处理哪个项目。
  applicationDirPath() = vividcode.exe 在哪，决定从哪里复制运行文件。

四、-g：生成命令到底做了什么
============================================================

入口是 ProjectStore.cpp 中的 VividCode::generate()。

步骤 1：建立 StoreAccess。
  它保存项目根路径、固定子目录 .vividcode 的路径，以及操作锁。
  canonicalRoot() 把项目目录转成明确的实际路径。
  checkTree() 检查已有生成目录，拒绝目录联接或符号链接。

步骤 2：检查查看器是否正在运行。
  如果项目的查看器正在使用运行文件，就提示先关闭，避免覆盖正在运行的 exe。

步骤 3：检查运行包。
  必须有 vividcode-viewer.exe、Qt6Core.dll、Qt6Gui.dll、
  Qt6Widgets.dll 和 platforms/qwindows.dll 等必要文件。
  -g 不会在每个目标项目重新编译一遍程序，而是复制已有运行文件。

步骤 4：处理 .vividcode/project.json。
  .vividcode 不存在：创建目录，写入初始 manifest。
  .vividcode 已存在：读取并验证其 project.json。
  已有目录但没有有效 manifest：拒绝覆盖，防止把不属于当前格式的数据当成项目。

步骤 5：将旧项目内的语义缓存校验迁移到共享 semantic，复制小启动器，清除旧运行附件。
  真实 Qt 查看器和分析器由 install-runtime.ps1 安装到共享 runtime，-g 不复制它们。

步骤 6：调用 recordSnapshot() 保存代码文件记录。
  无变化时复用最新记录；有变化时才新增历史。

步骤 7：提交 project.json 并输出启动器位置；不再生成 README.md。

生成示例：
  E:\MyProject\
      main.cpp
      MyClass.h
      .vividcode\
          vividcode-viewer.exe
          project.json
          records\
              record-某个UUID\
                  index.json

-g 不会自动弹出查看器，生成完成后可以双击它。
原始源码仍留在项目原来的位置。

五、ProjectScanner.h：程序怎么找到源码文件
============================================================

主要函数：scanProject(root)。
返回类型：ScanResult，包含 files、skippedDirectories、truncated。

  files：找到的文件相对路径，比如 src/main.cpp。
  skippedDirectories：因为排除规则跳过的目录数量。
  truncated：是否已经达到扫描数量上限。

可以把扫描过程理解成：
  把根目录放进“待查看目录”列表 pending。
  只要 pending 不空，就取出一个目录。
  查看目录中的条目：
    是目录 → 检查是否应该排除，不排除就放入 pending。
    是文件 → 检查扩展名，符合要求就放入 files。
  最后对 files 排序并返回。

支持 cpp、c、cc、cxx、h、hpp、hh、hxx、inl、ipp，以及 cs、py、pyw、pyi，
还有 JavaScript/TypeScript 的 js、jsx、mjs、cjs、ts、tsx 和 Java 的 java。
会排除 build、x64、.git、第三方依赖目录等，也会排除 .vividcode；
还会排除 C#/Python 的 bin、obj、__pycache__、venv 等生成目录，
以及 JS/TS 的 dist、node_modules、.next、.nuxt 和 Java 的 target、.gradle 等。

为什么必须排除 .vividcode？
  因为生成目录里有分析器源码和缓存，若再扫描它，就会把工具自身文件
  混进用户项目的记录，下一次生成还可能持续产生不必要的数据。

为什么用相对路径？
  同一个项目从 E 盘搬到 D 盘，src/main.cpp 的含义仍然不变。

当前限制：最多 5,000 个源码文件或 50,000 个目录条目。
查看器会提示扫描达到上限；记录模块会拒绝保存这次不完整的结果。
扫描在主线程执行，大项目可能暂时让界面没有响应。

六、recordSnapshot()：怎样判断代码有没有变化
============================================================

这部分负责“记录”，不是 C++ 语法解析器。

每个文件记录三项：
  path：项目内相对路径。
  bytes：文件大小。
  sha256：文件内容的哈希值。

哈希可以理解为从内容计算出来的一串摘要。
它用于比较内容变化，不能从哈希还原原来的源码。
例如把 return 0 改成 return 1，文件大小可能不变，但内容哈希会变化。
只改文件的修改时间，不改文件内容，不会因此产生新记录。

程序还会把整个有序文件清单算成一个 fingerprint。
用它和最新记录比较：
  一样 → 返回“代码未变化”，不增加历史。
  不一样 → 生成新的 record-<UUID> 目录。

UUID 是用于区分记录的标识，不是记录的时间顺序。
记录时间单独保存在 createdUtc 中。

每次新增记录包含：
  index.json：给程序读取的结构化数据。
  旧版 code.md 概览已取消，新版只有 JSON；旧 JSON 历史继续保留。

project.json 可以这样理解（下面是简化示意，不是可直接替换的真实文件）：
  latest = B
  history = [A, B]

意思是：已经登记过 A、B 两份记录，当前最新记录是 B。

保存顺序很重要：
  先原子保存新目录中的 index.json；
  再把记录 ID 加入 history；
  最后把 latest 指向新记录并提交 project.json。

如果新文档写到一半失败，原来的 latest 不会提前指向半份记录。
QSaveFile 用临时写入再提交的方式减少单文件被写坏的风险。
但整个运行包的复制不是一次整体事务，失败后仍可能需要重试 -g。

特别注意：当前记录不包含完整源码内容。
因此 -c 是清理旧文件概览，不是“保留最后一份源码备份”。

七、-c 和 -d：两个删除动作的区别
============================================================

-c 对应 cleanHistory()：
  1. 读取 project.json。
  2. 验证 latest 指向的记录存在且格式可读。
  3. 遍历 history，保留 latest，删除其余已登记的记录目录。
  4. 同步更新 history。

例如：
  清理前：history = [A, B, C]，latest = C。
  清理后：history = [C]，latest = C。

不会根据哪个文件的修改日期最大来猜测“最新”。
若最新记录损坏，会拒绝清理，避免把还能参考的旧记录也删掉。
用户手动放入的未知文件、没有登记的中断记录，不属于 -c 自动清理范围。

-d 对应 removeGenerated()：
  1. 计算当前项目下固定的 .vividcode 路径。
  2. 检查目标目录和运行锁。
  3. 删除整个 .vividcode。
  4. 目录原本不存在时，返回“无需删除”。

你的需求就是：-g 创建，-d 完整清理创建出来的目录。
生成的查看器、Qt 依赖、最新记录和旧记录都在 -d 的删除范围内。
将来若把分析索引纳入生成流程，索引也应一起删除。
程序不会删除 .vividcode 外的源码和人工维护的 Document 文档。

main.cpp 创建 QApplication，而不是 CLI 使用的 QCoreApplication。
因为图形程序需要窗口、绘图和鼠标键盘事件支持。

  app.setStyleSheet(...)：像 CSS 一样设置工具栏、输入框、页签和按钮的具体外观。
当前 Window 为 #101010，Base 为 #181818，Text/WindowText 为 #f0f0f0。
VividCode.cpp 里的画布和文件卡片不是普通文字控件，还需要设置画刷；
setBackgroundBrush 设置画布底色，setBrush 设置卡片文字和填充颜色。
界面主要由 VividCode.cpp 创建，因此只改 .ui 文件未必能改变这些控件。
修改后要重新编译并重启查看器。本次 build/Release 新程序已通过两组界面检查，
并目视检查 prototype-preview.png；没有主题切换按钮。

如果 exe 位于某项目的 .vividcode 目录：
  程序向上找一级，得到项目根目录；
  持有运行锁，防止 -g 和 -d 操作正在使用的运行文件；
  创建窗口；
  调用 window.openProject()；
  调用 window.show()；
  最后进入 app.exec()。

app.exec() 是事件循环：
  它等待按钮点击、鼠标选择、窗口关闭等事件，并分派给对应处理代码。
  不是一直重复扫描项目；只有打开或手动刷新等动作才触发相应扫描。

从普通 build/Release 目录双击查看器时，没有所属项目可自动定位。
此时可以点击“打开项目”，也可以传入项目目录参数；部署版自动打开上一级项目。

九、VividCode.h/.cpp：窗口是怎么工作的
============================================================

.h 头文件主要声明“有哪些成员和函数”；.cpp 实现“函数具体怎么做”。

主要控件：
  QTreeWidget：左侧文件树。
  QLineEdit：输入筛选文字。
  QGraphicsScene：保存文件卡片等画布对象。
  QGraphicsView：把 scene 显示在窗口中，支持平移和缩放。
  QPlainTextEdit：显示只读源码。
  QLabel：显示项目路径、文件路径等文字。
  QSplitter：让用户拖动分隔线调整区域大小。

主要状态：
  rootPath：当前项目目录。
  files：当前扫描到的文件相对路径列表。
  currentFile：目前正在显示的文件。

openProject() 的顺序：
  检查目录 → 扫描 → 更新 files → 清理失效的文件选择 → 重建视图。
  若原来的当前文件仍存在，就重新显示它。
  最后对已初始化项目调用 recordIfInitialized()。

recordIfInitialized() 不会随便给所有浏览的项目建目录。
只有项目已经有 .vividcode 时，才尝试保存或复用记录。

rebuildViews()：
  按筛选文字找匹配文件；
  根据路径的每一段建立目录树；
  为前 80 个匹配文件建立卡片；
  更新画布范围。

showFile()：
  确认文件属于当前列表 → 打开文件 → 检查大小 → 按 UTF-8 显示内容。
  大于 2 MiB 的文件不加载，避免基础版界面承受过大文本。
  源码控件只读，输入不会改动源文件。

十、connect 和 lambda：点击为何能调用函数
============================================================

构造函数里有这样的真实代码：

  connect(filter, &QLineEdit::textChanged, this,
          [this] { rebuildViews(); });

从左到右可以读成：
  当 filter 这个输入框发出“文字变化”信号，
  在当前窗口的上下文中，执行后面的那小段函数。

[this] { rebuildViews(); } 是一个 lambda，也就是临时写在这里的小函数。
[this] 表示它可以使用当前窗口对象，因而能调用窗口的 rebuildViews()。

其他几个连接类似：
  点击“打开项目” → 弹目录选择框 → openProject()。
  文件树当前项变化 → 取出保存的相对路径 → showFile()。
  卡片选择变化 → 取出卡片保存的相对路径 → showFile()。
  点击“刷新文件” → 对当前 rootPath 再调用 openProject()。

Qt::UserRole 是给树节点额外存数据的位置。
界面上可只显示 main.cpp，但节点内部可以保存 src/main.cpp，
这样不同文件夹里同名的文件仍能被正确打开。

重建树时为何使用 QSignalBlocker？
  清空和重新添加节点也可能触发选择信号。
  暂时阻断这些信号，可以避免重建过程中误调用 showFile()。
  离开作用域后，阻断对象析构，自动恢复信号。

十一、读这些代码时常见的 C++ 写法
============================================================

const QString &directory
  以只读引用接收字符串，避免不必要的复制，也表达“不修改参数”。

auto result = ...
  让编译器根据右侧推导类型。不是没有类型，也不是动态类型。

namespace VividCode
  把这一组函数放在 VividCode 名称空间中，减少重名。
  调用时写 VividCode::generate()。

匿名 namespace { ... }
  ProjectStore.cpp 中的内部辅助函数只在这个编译单元内部使用。
  对外接口放在 ProjectStore.h，调用者不用了解每个辅助函数的细节。

try / catch 和 attempt()
  内部函数用 fail() 抛出异常。
  attempt() 统一捕获异常，转成 Result{false, 错误说明}。
  CLI 或界面拿到 Result 后显示消息，避免每一层重复写报错逻辑。

Result{true, message}
  同时返回“是否成功”和“给用户看的文字”。
  recordIfInitialized() 在无需保存时也可能成功，但 message 为空。

RAII（对象生命周期管理资源）
  可以理解为：对象创建时接管资源，对象销毁时释放资源。
  本工程的 QFile、QLockFile、QSignalBlocker 和 unique_ptr 都体现了这种用法。

new 控件是否都要手写 delete？
  Qt 的父子对象和布局会管理许多控件；场景也管理加入其中的图形项。
  不能把“这里没写 delete”直接理解成泄漏，也不能推导出任意 new 都不用释放。

QLockFile 保护什么？
  .vividcode.lock：避免两个操作同时修改项目记录。
  .vividcode-viewer.lock：标记部署查看器正在运行，阻止覆盖或删除它的运行包。
  正常退出会释放锁；它们不是历史文档。

十三、.codegraph 能否改成 .vividcode：本次查证结果
============================================================

结论：本机 CodeGraph 1.6.0 支持改项目数据目录名。
配置入口是环境变量 CODEGRAPH_DIR，不需要为“只改目录名”修改其源码。

已检查到的安装位置：
  C:\Users\Lenovo\AppData\Local\codegraph\current\lib

依据：
  package.json：包名 @colbymchenry/codegraph，版本 1.6.0。
  dist/directory.js：codeGraphDirName() 读取 process.env.CODEGRAPH_DIR。
  dist/db/index.js：数据库路径使用 getCodeGraphDir()，数据库文件名为 codegraph.db。
  dist/mcp/daemon-paths.js：项目 daemon 路径使用 getCodeGraphDir()。

在单独测试进程中调用了本机真实函数，得到：
  不设置变量                    → .codegraph
  CODEGRAPH_DIR=.vividcode       → .vividcode
  getCodeGraphDir(E:/sample-project)
                                → E:\sample-project\.vividcode
  isCodeGraphDataDir(.vividcode) → true
  CODEGRAPH_DIR=.vividcode/codegraph-index
                                → 配置无效，警告并回退 .codegraph

所以它支持单层目录名，不支持带斜杠的嵌套相对路径。
之前提到的 .vividcode/codegraph-index 不能直接作为此版本的环境变量值。

PowerShell 的临时设置写法是：
  $env:CODEGRAPH_DIR = '.vividcode'

这只影响当前 PowerShell 和之后由它启动的子进程。
不会迁移已有数据库，也不会改变已经运行的 MCP 服务或 daemon。
实际迁移还要让相应 MCP/CLI/daemon 启动环境保持一致，并正确重启它们。

另一个边界：该变量只改变项目数据目录名。
不会把 codegraph 命令名、codegraph_explore 工具名或 codegraph.db 文件名一起改掉。
用户主目录中的全局 .codegraph/daemons 注册目录也不由这个变量改名。

十四、为什么查到能改，还不能直接把当前文件夹改名
============================================================

不是因为要保留索引不让 -d 删除；你已经明确要求生成和删除成对。
真正需要衔接的是两个程序对同一个目录的使用流程。

当前代码的实际情况：
  1. vividcode -g 不会启动 CodeGraph，不会生成 codegraph.db。
  2. vividcode -d 只检查自己的运行锁，不会停止 CodeGraph 的 daemon。
  3. 把纯 .codegraph 目录直接改名后，它还没有 vividcode 的 project.json。
     现有 -g 会把它视为未知的已有目录，拒绝覆盖。
  4. 当前 CodeGraph 索引由正在运行的服务管理，有数据库及 WAL/SHM 文件。
     迁移必须让数据库干净关闭后处理，不能只搬动一个 db 文件就认为完成。

如果后续要统一目录，合理的衔接顺序是：
  先由 vividcode 初始化自己的存储结构；
  让 CodeGraph 在相同项目根目录、CODEGRAPH_DIR=.vividcode 的环境中使用索引；
  接好服务停止、数据库迁移、重新连接和生成/删除流程；
  删除时先释放索引服务占用，再删除整个 .vividcode；
  验证 AI 查询仍能用，且删除后不被旧服务重新建回。

将来统一后的一个可行目录形态是：
  .vividcode\
      project.json
      vividcode-viewer.exe
      records\...
      codegraph.db
      daemon.pid 等 CodeGraph 运行文件

这里只是已核实配置能力后的接入方案，尚未实现迁移或接入。
用户随后取消了这项迁移：本项目继续使用原来的 .codegraph；没有移动 .codegraph，没有改全局或 MCP 环境变量，也没有改第三方工具代码。
vividcode 的 .vividcode 仍然只管理 vividcode 自己生成的文件。

十七、语法检查为什么会提到 LLVM
============================================================

LLVM 是编译器基础设施项目；Clang 是其中面向 C/C++ 等语言的编译器前端。
前端负责理解源码，进行语法、类型等分析。libclang 提供可供程序调用的 C 接口。
仅检查 C++ 能否编译时，现有 MSVC 也能报告语法和类型错误，并非必须安装 LLVM。
vividcode 想进一步提取类、函数、定义位置与关系，所以计划使用 libclang。
仍然可以用 MSVC 编译 vividcode，同时让它调用 libclang 分析用户的 C++ 源码。

接入需要核实头文件、链接库和 libclang.dll，而非只确认 clang.exe 存在。
解析还需要目标项目的头文件搜索路径、宏和语言标准等，可从 compile_commands.json 导入。
libclang 并不暴露 Clang 全部 AST 能力；复杂模板、指针和动态调用不能保证全部还原。
当前程序仍为文件级浏览与记录，尚未新增语义解析功能。2026-09-27 用户已报告 LLVM
安装完成；实际版本、安装路径和 libclang 开发/运行文件的可用性尚未核验。
产品目标是长期使用的真实分析工具；本文面向初学者解释现有代码，不限制未来规模。
允许混合语言，但分析器使用 C++ 还是 Python、是否独立进程尚未定案，见开发讨论.txt。
