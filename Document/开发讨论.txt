一、当前产品定位与实现
======================
用户明确：vividcode 要成为以后持续使用的真实代码分析工具，不能以课程作业或小项目
的视角限制目标。课程展示是交付场景。以长期可用性设计，以可验证的小步增量实现。
当前仍只有文件级浏览与记录管理，支持读取 C/C++、C#、Python、JavaScript/TypeScript、
Java 文件；尚无任何语言的类、函数或调用关系语义分析。扫描上限、主线程扫描和卡片数量
是当前限制，不是产品目标。2026-09-27 已把文件级浏览扩展到 JS/TS/Java，仅扩展名与
排除目录，未接入语义解析；详见八。

三、已确定要求与尚未定案的方案
============================
用户已确定：
1. 不强制全用 C++，允许使用其他语言以提高开发效率；同时不能因赶作业牺牲真实分析
   能力和长期使用价值。语言数量不是目标，复用已有工程，避免无收益的全面重写。
2. 符号身份与显示名称分离，关系连接独立 ID；C++ 方向基于 Clang USR，不靠名称猜调用。
3. 图形采用 LOD 分级：先显示文件，缩放后逐步显示类、方法、变量及相应关系。
4. 语义索引缓存采用 SQLite。现有文件级记录 JSON 不是语义索引，暂不因此迁移它。
5. 打开后检查变化并更新、依赖驱动增量的设计方向继续保留；不得阻塞界面等待分析。
6. -g/-d 成对管理 .vividcode 内生成的程序、记录和未来分析索引；CodeGraph 的
   .codegraph 保持原状，不迁移、不视为 vividcode 自己的分析服务。

候选方案（助手建议，未成为最终选型）：
- 复用现有 C++ / Qt 界面与控制台，将分析职责从界面中分离。
- 曾建议 C++ / Qt + Python 调用 libclang，用独立程序及 JSON 交换结果。
- 随后按长期目标建议优先考虑 C++ 独立分析进程，Python 可做辅助开发工具。
- 两者均未定案。语言、进程/线程边界、通信协议、数据库写入归属应依据验证选择。
  不默认引入 Python 运行时，也不把“全部 C++”恢复为强制要求。
- 优先验证 libclang 的语义能力；不足时评估更深入的 Clang 接口，不宣称 libclang
  暴露全部 AST 或能够完整还原任意模板、指针及动态调用。
- SQLite 已定，但 Qt6::Sql 是 Qt 访问数据库时的实现候选；若使用才需要部署 qsqlite。
- 允许随运行包部署分析依赖；具体文件、体积、Python 是否需要打包均待选型和实测。
- 多语言语义分析（用户已明确先做文件级浏览，语义稍后再做）：JS/TS 可用 TypeScript
  编译器或 tree-sitter，Java 可用 javaparser / Eclipse JDT / javac 编译器 API，
  C# 用 Roslyn，Python 用标准库 ast；JS/Java 不依赖 LLVM。tree-sitter 只给语法树，
  符号解析、类型与引用关系仍需各语言的语义工具。以上均为候选，未选型、未接入。

历史方案处理：
原“方案 B+：查看器内嵌 libclang + JSON 缓存”不再是当前固定架构。
自动刷新要求运行包能够触发分析，并不要求解析一定发生在查看器进程内。
JSON 可用于现有记录或候选通信协议，不能替代已经确定的 SQLite 语义缓存方向。

四、长期分析能力的设计与验收要求（尚未实现）
==========================================
- 编译配置：尽早验证 compile_commands.json 导入、工作目录、宏、头文件路径、语言
  标准及配置隔离。其生成方式取决于实际构建系统，不假定现有 VS 生成器能直接导出。
  缺失配置时可显式手配并降级分析，但必须保留诊断，不能显示为完整成功。
- 准确性：关系有源码发生位置及解析状态；同名、重载、声明定义、跨 TU 和内部链接
  身份需要样例验证；无法确定的目标显示未解析或可能调用，不伪造确定连线。
- 增量：按 TU 和配置保存结果，用依赖图将头文件变化传播到受影响的 TU；源码删除、
  编译参数、解析器版本变化也要使相应缓存失效。全量重建仅可作早期验证或恢复策略。
- 一致性：规划事务提交、索引版本、重建/迁移、失败后保留旧结果并标记过时；避免
  部分失败覆盖有效索引或跨配置混用结果。
- 交互：先展示可用缓存并标记新旧状态，后台刷新；规划进度、取消、重试和局部更新。
  当前 F5 仍是文件级刷新；未来语义增量刷新与强制全量重建的入口需分别定义，不能
  把“F5 清缓存全量解析”当成已实现行为。
- 资源与稳定性：验证内存、并发上限、取消、异常恢复和 UI 响应；独立进程是故障隔离
  候选，不是已实现保证。
- 扩展：统一符号、关系、位置和诊断模型，为其他语言保留接入位置；C#/Python 的
  文件浏览已实现，语义分析尚未实现，其分析器选型也未定。
- 分发：分析程序、DLL、可选语言运行时需纳入生成与清理生命周期，验证干净机器部署。
- AI 修改后可复用刷新入口，改动列表作为输入；仍需结合依赖和配置决定受影响 TU。
  AI 接口、自动改码和商业系统仍为后续设想，不因长期目标获得本轮实现授权。

五、性能与验证证据
==================
撤回此前未实测的“缓存毫秒级”“改动秒刷”“1000 文件 1~5 分钟”“解决大项目 90%
痛点”等量级承诺，以及 libclang/Qt 部署大小的固定估算。不能作为验收结论。
后续在可复现环境记录：项目/提交、TU 数量、构建配置、硬件、分析器版本、冷启动与
热启动、全量/增量耗时、峰值内存、界面响应、诊断覆盖及取消恢复结果。
性能目标应根据真实使用项目和测量结果制定，不因只有文件数就推断解析耗时。

1. 核验 LLVM 安装和调用条件，选定最小验证方式；用 demo 及针对性样例验证编译参数、
   声明定义、重载、跨文件调用、源码位置及失败诊断，而不是只打印类名。

   编译选项变化、失败和重试，不把依赖和编译参数视为最后才补的可选优化。
4. 接入 Qt 关系展示、源码定位和 LOD，验证后台任务、取消及旧结果提示。
5. 逐步扩大真实项目规模，测量性能与资源，完善运行包及 -g/-d 生命周期、版本升级
   和干净机器部署。大型 Unreal 工程需专门验证，不作未测试的支持承诺。
阶段可按依赖调整；具体下一项工作以用户请求为准。

七、符号模型细节（保留的讨论建议，尚未实施）
==========================================

2026-09-26 补充：符号 ID 与关系模型建议（讨论方案，尚未实现或实测）
- 名称、身份、源码出现位置分开保存。qualifiedName/signature 用于展示；
  C++ 符号优先以 canonical declaration 的 Clang USR 作为身份依据。
  项目内可先用 cpp:usr:<原始USR>，无需自造签名编码或先做哈希。
- 同类重载、const/non-const 成员分别建符号；声明与定义合并到同一符号，
  保存多个声明/定义位置。返回类型不能单独用来区分普通函数重载。
- 引用处通过 clang_getCursorReferenced 获取目标，再规范化并取 USR；
  不通过名称字符串查找目标。编译参数不全或模板依赖等无法解析时保留
  unresolved 和现场位置，不任选同名节点。虚调用记录静态目标及 virtual
  分派标记，不将静态目标描述成唯一运行时实现。
- Symbol 建议字段：id、kind、name、qualifiedName、signature、parentId、
  declarations[]、definitions[]；源码位置包含文件、行列、字节范围。
- Relation 建议字段：fromId、可空 toId、kind、site、resolution、dispatch；
  每条关系另保留 originTu/configId，支持增量替换和配置隔离。
  首版 Contains/Inherits/Calls/References；Reads/Writes 后续细化。
- 相同起终点的多次调用保存多个现场，界面可聚合一条线并显示次数。
  头文件被多个 TU 解析时，按现场去重展示，底层保留来源集合，避免重复
  计数及删除一个 TU 时误删其他 TU 仍提供的关系。
- 内部链接实体（尤其头文件内 static/匿名命名空间）必要时加 TU 身份，
  不能把所有符号都加 TU，否则会拆散普通跨文件符号。无 USR 时只能用
  父符号+文件+字节位置+种类等生成带配置/TU作用域的临时 ID，并标明
  不保证编辑后稳定。USR 也不保证跨重命名、移动及 Clang 版本永远不变。
- 首版建议只显示一个选定编译配置，缓存记录工具版本和配置指纹；
  身份键的细节须用重载、遮蔽、跨 TU 声明定义、内部链接样例验证。
- 2026-09-26 当时仅查阅官方 API 文档并更新讨论，没有编写或运行语义解析代码。
  参考：https://clang.llvm.org/doxygen/group__CINDEX__CURSOR__XREF.html
